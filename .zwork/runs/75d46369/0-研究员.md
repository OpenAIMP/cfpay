## Slack

Slack does support this: "The Slackbot MCP Client connects remote MCP servers to Slack… Slackbot discovers your server's tools and invokes them" (docs.slack.dev/ai/). Config path: api.slack.com/apps → Features → **MCP Servers** → Get Started; you supply the URL `https://pay.openaimp.com/mcp`. **Whether Slack accepts an unauthenticated server is unverified** — every `docs.slack.dev/ai/slackbot-mcp/*` fetch failed this run, and Slack routes connectors through admin approval. Test interactively; if it's rejected, that's the trigger to add auth rather than to weaken the tool set. Note 0.4.1's `ServeOptions` has only `binding`/`corsOptions`/`transport`/`jurisdiction` — no `allowedHostnames`, so you can tighten `corsOptions.origin` but cannot pin host/origin the way the v2 guide shows.

## Ranked risks

1. **Funds/payment-bypass surface** — the two methods above; keep the MCP tool list disjoint from spending `@callable`s.
2. **Irreversible DO migration state** — `v1`/`v2` are live; append-only `v3`, never reorder.
3. **No tests; `tsc --noEmit` is the only gate** — CI runs `npm ci` → typecheck → deploy, so a type-clean-but-wrong handler ships straight to prod.
4. **Second unauthenticated entry point on the domain that also serves x402 payments and the dashboard** — read-only tools + narrowed CORS only.
5. **SDK drift** — the forced v2 upgrade will touch `agents`, which also powers the live email path; keep `src/mcp.ts` import-isolated.
6. **Demo/reference mismatch** — copy the pattern, not the config (missing `MCP_OBJECT`, mixed v1/v2 deps).
7. **Future upgrade mechanics** — exact-pinned MCP versions + `legacy-peer-deps` + stale lockfile = `npm ci` failure; isolate in its own PR.
8. **Tool-arg SSRF** — any future URL-accepting tool needs the `isTrustedResponseUrl`-style allowlist.
