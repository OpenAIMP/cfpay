**5. Idempotency.** Why current storage fails: each delivery is appended to `webhookEvents` with a fresh `generateId()` — no uniqueness key, no dedupe, unbounded growth. Design (additive JSON state, no DO migration): `stripeCheckouts: Record<sessionId, {requestId, status: 'awaiting_session'|'session_created'|'fulfilled'|'expired', email, request, sessionUrl?, createdAt, fulfilledAt?, eventId?, paymentIntentId?}>` + bounded `stripeProcessedEvents: Record<eventId, receivedAt>`. One-shot `session_created → fulfilled`; duplicate/re-ordered events are no-ops; `client_reference_id`/`metadata.cfmail_request_id` fallback re-binds a checkout even if the session-id write was lost; third guard: refuse if a PaymentRecord with that session id already exists. Rationale quotes: "Track event IDs to identify duplicate deliveries" and events may arrive out of order (https://docs.stripe.com/webhooks). Session double-click: reuse a `session_created` record for same email+request within a short window.
